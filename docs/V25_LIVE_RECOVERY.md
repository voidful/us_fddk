## 準備新觀察段

在明確決定封存中斷的舊觀察段、由現在重開以前，不要啟用新段。以下工具只準備
可覆核資料，不改寫既有三帳戶、收據、網站或凍結合約，也不推送或部署：

```bash
./.venv/bin/python scripts/prepare_v25_live_segment.py \
  --directory /tmp/v25-new-segment
```

目錄必須不存在。正式入口採真實 UTC 時鐘，沒有可回填日期的參數；可選用
`--snapshot`，但其截止日仍須是現在最近已完成的 XNYS session。
只有舊三帳戶一致、收據鏈驗證通過，而且存在多 session 缺口時才允許準備新段。

輸出包含：

- `prior/`：舊三帳戶及舊收據鏈的逐位元組副本。
- `v25_segment_manifest.json`：舊檔 SHA-256、舊收據鏈頭、新起點、觀察時間及未啟用狀態。
- 新三帳戶：同起點、同快照、同初始資金、同成本；全現金、僅一筆起始權益，
  委託只可於之後的 session 成交。
- 新前瞻證據：新增 session、已成交配置及已完成再平衡都從零開始。
- 新空收據鏈：不接上舊的前瞻計數；舊鏈獨立保存。

252 個新增交易日、6 次初始配置後月度再平衡、兩個基準及 Newey–West 門檻全部保持
原定義。新段不能繼承舊績效，也不能以重開規避既有帳戶或收據完整性錯誤。

## 實際恢復 main 所需步驟

1. 修復分支的 `v25 repair CI` 全部通過並覆核 diff；這個 workflow 只有 contents:read，
   不抓取新行情、不修改遠端、不建置或部署網站。
2. 確認 main 合併引起的 GitHub Pages 部署已獲授權，再合併修復 PR。
   `pages.yml` 監聽 main push；修復分支 push 和 PR 更新本身不觸發它。
3. 覆核新觀察段的 manifest，明確授權其啟用。將 `prior/` 和 manifest 先保存為可追蹤、
   不可覆寫的封存；把新段三帳戶、證據及獨立收據鏈設為 active。不得直接刪除舊段
   或把舊收據接入新計數；這一步應另以資料變更 diff 覆核。
4. 重新匯出網站、核對三帳戶、以新段追加初始收據並檢查發布門檻，然後才保存資料。
   舊 frozen research 與 promotion contract 必須沒有 diff。
5. 到下一個真正新增的 session 執行 daily，確認三帳戶只新增一日、初始配置才成交、
   初始配置不計為月度再平衡。之後才稱為日更恢復。

daily 本身有 main 寫入及 Pages dispatch，因此不能當成不涉及部署的測試重跑。
修復 PR 合併本身也不會重開已中斷的 LIVE 觀察段。
